# Architecture and data boundaries

One deployable PHP 8.3 application with a browser-rendered UI and PDO SQLite database. Hostinger's inspected Cloud Economy plan already serves many Node.js apps; this application consumes no Node.js app slot. PDO SQLite and cURL were enabled on the existing PHP configuration. No hosting, domain, API or database subscription was purchased.

`index.php` applies headers and session policy, exposes a public shell and authenticates every data/admin route. Mutations require POST plus a session CSRF token. Webhooks are the sole public mutation route and require a recent raw-body HMAC signature. Owner passwords are hashed; sessions regenerate on login, expire after eight hours, use HttpOnly/SameSite cookies and Secure cookies on HTTPS. Login attempts are limited per remote address. No multi-user access, password reset email, or external authentication provider is claimed.

`server/core.php` implements domain writes and the explainable rubric. `server/schema.sql` is an idempotent version-1 migration: opportunities, evidence, evidence links, structured records, decision history, sources, jobs, checkouts, webhook events, refunds and login buckets. Foreign keys enforce opportunity/evidence/payment record relationships. Structured record payloads are JSON, with typed PHP boundaries and SQL constraints for relational identity. This first migration is additive; it imports none of the legacy fixed ideas.

Collection is a source-adapter interface and persisted queue, not a hardcoded feed. The worker atomically leases a single job; stale leases can be reclaimed. One job makes one bounded external API call. It stores results and success state together, retries at most three times, respects provider backoff and stops for exhausted quota. Scheduler enqueueing honors profile opt-in and source limits. SQLite's WAL and busy timeout handle short overlapping UI/worker transactions.

Payment identity connects a checkout to an offer, product and experiment for one opportunity. The submitted browser amount is ignored; amounts come from stored sandbox offer records. Checkout creation uses a stable per-request idempotency key. Only a verified paid event can set `fulfilled_at`. Event ID and session ID constraints prevent duplicate revenue/fulfillment. Refunds retain the greatest provider cumulative total, including events received before the paid event. Payment ledgers are mode-separated; the current release rejects all live keys/events. Dashboard live revenue is therefore zero until future approved selling work enables it. No subscription revenue is inferred from one-time payments.

External strings enter the DOM only after HTML escaping; URLs accept HTTP(S) only. The collection adapter constructs fixed HTTPS provider URLs and never fetches a URL supplied by source text or the user. Imported text cannot run tools, change instructions, or invoke a model. Raw provider errors, credentials and webhook bodies are not logged. Database files live outside `public_html`; config lives in a denied server directory and is PHP code with no output. Direct config/schema/Git-path denial was verified on staging.

The frontend is dependency-free browser JavaScript with JSDoc annotations. PHP code uses strict types. The first UI focuses on compact comparisons, explicit unknowns and stage-specific records. There is no browser-local data store.
